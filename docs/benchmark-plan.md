# 지표·벤치마크 환경 정의 (v0.1, W1 초안)

> 목적: 12주 동안 **무엇을, 어떤 조건에서, 어떻게 재고, 어떻게 보고할지**를 미리 정한다. 측정 조건이 없는 수치는 포트폴리오에서 신뢰를 잃기 때문이다.
> 상태: 초안. 팀원 검토 후 W1 말 "계약 확정"에서 고정한다. 클라우드 사양처럼 아직 못 정하는 값은 7장에 모아 두었다.
> 관련 문서: `docs/threat-model.md`(왜 재는가), `docs/api/message-spec.md`(결과 코드), `docs/erd/erd.md`(검사할 테이블)
> 읽는 법: 2장이 한눈에 보는 표이고, 3장이 지표별 자세한 방법이다. 직접 측정할 때는 4장(환경 기록)과 5장(보고 양식)을 따른다.

## 1. 원칙

1. **측정 조건 없는 수치는 쓰지 않는다.** 모든 결과에 4장의 환경 기록을 붙인다.
2. **성능·AI 결과는 미리 정하지 않는다.** 목표 숫자를 먼저 정하고 맞추는 것이 아니라, 측정값과 그 원인을 그대로 보고한다. "병목이 아니었다"도 정당한 결과다.
3. **한 번에 한 가지만 바꾼다.** 모드(LEGACY, HYBRID, PQC)를 비교할 때 나머지 조건은 같게 둔다.
4. **반복해서 잰다.** 같은 조건을 3회 이상 재고, 중앙값과 최솟값·최댓값을 함께 적는다.
5. **정합성·보안 지표는 자동 테스트로 남긴다.** 한 번 손으로 확인하는 것이 아니라 CI에서 매번 돌아가야 증거가 된다.
6. **진단의 평가용 데이터는 개발에 쓰지 않는다.** 규칙을 만들거나 모델을 학습할 때 본 데이터로 점수를 내지 않는다.

## 3. 지표별 측정 방법

### 3-1. 금융 정합성 (M1)

**시나리오(초안 제안)**
- 계좌 100개, 초기 잔액을 고정한다.
- 이체 요청 1,000건 이상을 가상 사용자 50~100명으로 동시에 보낸다.
- 그중 약 20%는 같은 `idempotency_key`로 다시 보낸다(재시도 흉내).
- 일부는 일부러 잔액 부족으로 만든다.

**끝난 뒤 검사하는 것(SQL로 확인)**

| 검사 | 기대 |
| --- | --- |
| 모든 전표(`journal`)에서 차변 합계와 대변 합계 비교 | 항상 같음 (규칙 R2) |
| 계좌별 `balance`와 `ledger_entry` 합계 비교 | 항상 같음 |
| `idempotency_key` 하나당 `POSTED` 전표 수 | 0 또는 1 |
| 내부 계좌끼리만 이체하는 시나리오에서 전체 잔액 합계 | 시작할 때와 같음 |

**보고**: 보낸 요청 수, 성공·실패·중복 응답 수, 위 검사 결과.

### 3-2. 보안 시험 (M2, M3)

모두 자동 테스트로 만들어 CI에서 돌린다. 기대 결과는 `message-spec.md` v0.2의 결과 코드다.

| 시험 | 공격 | 기대 결과 | 위협 |
| --- | --- | --- | --- |
| 다운그레이드 1 | 기업의 최저 모드(`crypto_floor`)보다 낮은 모드로 요청 | `E1003` | T2 |
| 다운그레이드 2 | 서명한 뒤 `crypto_mode`만 허용 범위 안의 다른 값으로 바꿔 전송 | `E1001` (모드가 서명에 포함되기 때문) | T2 |
| 재전송 1 | 같은 요청을 5분 안에 다시 전송 | `E1002` (nonce 중복) | T3 |
| 재전송 2 | 같은 요청을 5분 지나 전송 | `E1002` (시간 범위 초과) | T3 |
| 변조 1 | 본문 1비트를 바꿔 전송 | `E1001` | T5 |
| 변조 2 | HYBRID에서 서명 둘 중 하나만 틀리게 전송 | `E1001` (둘 다 통과해야 성공) | T5 |
| nonce 선점 | 서명이 틀린 요청을 보낸 뒤, 같은 nonce의 정상 요청을 보냄 | 정상 요청 성공 (서명 확인 뒤에 nonce를 등록하기 때문) | T3 |
| 단독 이체 | 만든 사람이 직접 승인 | `E2006` | T6 |
| 단독 정책 변경 | 요청자와 같은 사람이 정책 변경을 승인 | 거부 (규칙 R8, DB 제약) | T13 |
| 감사 로그 변조 | 중간 행을 고친 뒤 해시 체인 검증 | 고친 위치에서 검증 실패 | T7 |
| 시크릿 노출 | 저장소와 로그를 시크릿 스캐너로 검사 | 0건 | T9 |

### 3-3. 성능과 무중단 전환 (M4, M5)

**비교 조건**: 모드 3가지(LEGACY, HYBRID, PQC) × 세션 키 캐시 켬·끔 = 6가지. 나머지 조건은 모두 같게 둔다.

**잴 것**
- TPS(초당 성공 건수), 지연의 P50·P95·P99, 오류율
- 요청 전문 크기(바이트). 서명·키 교환 부분과 이체 내용 부분을 나누어 적는다
- 구간별 시간: 키 교환, 서명 검증, 복호화, DB 쓰기. PQC가 느린지보다 **어느 구간이 지배적인지**가 핵심이다
- 서버 CPU 사용률

**절차(초안 제안)**
1. 부하를 단계적으로 올려 오류율이나 지연이 급증하는 지점(포화점)을 찾는다.
2. 지연은 포화점보다 낮은 일정한 요청률로 따로 잰다.
3. 각 조건마다 워밍업 60초는 버리고 5분을 측정하며, 3회 반복한다.

**무중단 전환 시나리오(M4)**
1. 포화점의 절반 정도 일정한 부하를 5분간 보낸다.
2. 중간에 기업 모드를 LEGACY → HYBRID → PQC 순으로 바꾼다. 구·신 모드를 함께 허용하는 기간을 둔다.
3. 전환 전후의 실패 요청 수, 지연 변화를 기록한다.
4. 모드를 되돌리는 롤백도 같은 부하에서 한 번 시험하고 걸린 시간을 적는다.

**보고**: 실패 0건이면 그대로, 아니면 몇 건이 어떤 코드로 실패했고 원인이 무엇인지.

### 3-4. 장애 주입 (M6)

| 장애 | 주입 방법 | 확인할 것 |
| --- | --- | --- |
| Redis 다운 | 컨테이너 중지 | nonce를 확인할 수 없는 요청이 **거절**되는지(7장 결정 사항), 복구 후 정상 처리 |
| Redis 강제 종료 후 재시작 | 요청 직후 `docker kill`(정상 종료가 아님) → 재시작 → **같은 요청 재전송** | `E1002`(재전송)가 나오는지. Redis AOF 기본 설정(`appendfsync everysec`)은 1초마다 저장하므로, 직전 1초 안의 nonce가 사라져 재전송이 통과할 수 있다. 통과하면 `appendfsync always`로 바꿀지 결과를 보고 정한다. 이때도 멱등성 키 덕분에 이체가 두 번 생기지는 않는지(중복 0건) 함께 확인한다 |
| DB 지연 | Toxiproxy로 지연 추가 | 타임아웃과 재시도가 일어나도 중복 이체 0건 |
| 네트워크 단절 | Toxiproxy로 연결 끊기 | 재시도 때 `idempotency_key`로 중복 없이 한 번만 처리 |
| 게이트웨이 재시작 | 컨테이너 재시작 | 진행 중 요청 처리, 세션 키 재협상 |

**보고**: 데이터 손실 건수, 중복 건수, 복구 시간(장애를 발견한 때부터 정상 처리를 다시 시작한 때까지).

### 3-5. 진단 정확도 (M7)

**용어(쉬운 말)**
- **정밀도(Precision)**: 도구가 "취약하다"고 한 것 중 진짜 취약한 비율. 낮으면 오탐이 많다.
- **재현율(Recall)**: 진짜 취약한 것 중 도구가 찾아낸 비율. 낮으면 놓치는 게 많다.
- **F1**: 둘을 합친 점수.

**정의(초안)**
- 양성(찾아야 하는 것): 양자컴퓨터에 취약한 공개키 알고리즘(RSA, 타원곡선 계열, DH, DSA 등)을 실제로 선택해서 쓰는 코드 위치
- 평가 단위: 암호 호출 위치 1건을 케이스 1건으로 센다. 현재 `tools/diagnosis/samples/Cases.java`와 같은 방식이다. 다만 CodeBERT는 호출 한 줄만으로는 알고리즘 값이 어디서 왔는지 알 수 없으므로, **모델 입력은 그 호출을 감싼 메서드 전체**로 한다. 점수는 어느 방법이든 호출 위치 단위로 매긴다
- 클래스(라벨) 세 가지
  - `VULNERABLE`: 양자 취약 공개키를 사용한다 (규칙의 ERROR)
  - `SAFE`: 양자 취약이 아니거나, 암호처럼 보이지만 암호가 아닌 코드
  - `REVIEW`: 알고리즘이 실행 중에 정해져서 코드만으로는 판단할 수 없다 (규칙의 WARNING)
- 비교 방법 4가지: 정규식, Semgrep·AST, CodeBERT, 결합

**평가 세트 규칙**
- 고유 케이스 500건 이상, 평가 전용 숨긴 케이스 50건 이상
- 클래스별 150건 이상을 **목표**로 한다. `VULNERABLE`과 `SAFE`는 채우는 것을 기본으로 보고, `REVIEW`는 공개 코드에서 서로 다른 사례가 많지 않아 못 채울 수 있다. 못 채우면 **실제로 채운 건수와 그 이유**를 보고서에 적는다(조용히 합성 데이터로 채우지 않는다)
- 복사본(포크 등) 중복을 제거한다. 학습용과 평가용에 같은 코드가 섞이면 점수가 부풀려진다
- 숨긴 케이스는 규칙 작성과 모델 학습에 쓰지 않고, 판정 시점(W4)과 최종(W11)에만 평가한다. 같은 세트를 보고 규칙을 고치기 시작하면 더는 숨긴 세트가 아니다
- 라벨은 사람이 붙이고, 일부(초안 20%)는 두 사람이 따로 라벨해서 불일치를 확인한다

**현재 시험과의 구분**: `run-tests.sh`가 도는 28개 케이스는 **규칙이 의도대로 동작하는지 확인하는 회귀 시험**이다. 만든 사람이 문제를 낸 것이므로 정확도 수치로 쓰지 않는다.

**보고**: 비교표, 오탐·미탐 사례 목록, 방법별 한계. AI가 규칙보다 나은지는 숨긴 케이스 결과로만 말한다.

### 3-6. DB·배치와 복구 (M8, M9)

- **배치**: 이체 1만 건을 대량 처리하는 시간과 처리량(건/초). 한 번에 묶는 크기(청크)를 바꿔 가며 비교한다.
- **실행계획**: 핵심 쿼리 3~5개(중복 키 확인, 잔액 조회, 대사 합계, 감사 로그 검증 등)를 `EXPLAIN (ANALYZE, BUFFERS)`로 튜닝 전후 비교한다. **데이터 행 수를 함께 적는다.** 행이 적으면 인덱스 효과가 보이지 않는다.
- **복구**: 백업 → 빈 DB에 복원 → 대사 배치 재실행 → 불일치 0건 확인, 전체 걸린 시간 기록.

## 4. 측정 환경 기록 양식 (모든 측정 결과에 붙인다)

| 항목 | 적을 것 |
| --- | --- |
| 날짜, 코드 버전 | 측정일, Git 커밋 해시 |
| 환경 구분 | 로컬(Docker Compose) 또는 클라우드 |
| 머신 | CPU 코어 수, 메모리, 디스크 종류 |
| 소프트웨어 | OS, Java, Bouncy Castle, PostgreSQL, Redis 버전 |
| 설정 | JVM 옵션, DB 연결 풀 크기, 주요 DB 설정 |
| 네트워크 | 구성 요소가 같은 머신인지 다른 머신인지, 추가한 지연 |
| 데이터 크기 | 기업·계좌·이체 건수 |
| 부하 | 도구와 버전, 스크립트 경로, 가상 사용자 수, 요청률 |
| 조건 | 암호 모드, 세션 키 캐시 켬·끔 |
| 반복 | 반복 횟수, 워밍업 시간, 측정 시간 |

**환경 단계**
- **로컬(Compose)**: 개발 중 사전 측정. 결과에 "로컬 측정"이라고 표시한다.
- **클라우드**: W8 배포 이후의 최종 측정. 포트폴리오에 싣는 성능 수치는 클라우드 측정만 쓴다.
- 부하를 만드는 프로그램과 측정 대상 서버는 가능하면 다른 머신에 둔다. 같은 머신이면 서로 자원을 뺏어 수치가 왜곡되므로 그 사실을 적는다.

## 7. 아직 정하지 않은 것 (팀이 정할 것)

1. 클라우드 선택(AWS 또는 NCP)과 머신 사양. 정해지면 4장에 적는다
2. 반복 횟수(초안 3회), 워밍업(초안 60초), 측정 시간(초안 5분)
3. 부하 발생기를 둘 위치(같은 VM 또는 다른 VM)
4. 정합성 시험의 데이터 크기(초안: 계좌 100개)
5. CI에서 자동으로 돌릴 범위. 초안: 보안·정합성 시험은 CI, 부하·장애 시험은 수동
6. Redis AOF 저장 주기: 기본값(`appendfsync everysec`)을 쓸지 `always`로 바꿀지. 3-4절의 "Redis 강제 종료 후 재시작" 시험 결과로 정한다(`docs/infra/network.md`의 nonce 유실 질문과 같은 문제)

**결정된 것** (팀 합의)
- 진단 평가 단위: 호출 위치 1건. CodeBERT 입력만 그 호출을 감싼 메서드 전체로 한다(3-5절)
- Redis가 죽었을 때: nonce를 확인할 수 없는 요청은 **거절**한다. 금융 이체이므로 재전송 방어가 서비스 가용성보다 우선이다. 거절하면 Redis가 멈춘 동안 이체가 멈춘다는 점은 알고 있고, 3-4절에서 복구 시간으로 측정한다
