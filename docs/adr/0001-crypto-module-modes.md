# ADR-0001: 암호 모듈은 3가지 모드를 같은 인터페이스로 제공하고, HYBRID는 두 비밀을 HKDF로 결합한다

- 날짜: 2026-11-26
- 상태: 제안
- 작성자: 팀원 B

## 배경

게이트웨이(DMZ)와 기업 시스템 시뮬레이터는 같은 방식으로 서명·키 교환·암호화를 해야 한다. 전문 규격(`docs/api/message-spec.md`)은 서명 형식(`signatures`의 `alg`, `kid`, `value`)과 모드별 서명 개수를 정했지만, **세션 키를 만드는 키 교환과 본문 암호화 방식은 아직 정하지 않았다**(`openapi.yaml`에도 "전송 구간 암호화는 범위 밖"). 위협 모델의 T1(HNDL), T2(다운그레이드), T5(요청 변조)를 막으려면 이 부분을 W2에 정해야 한다.

## 선택지

1. **모드마다 다른 코드 경로**: 단순하지만 게이트웨이가 모드별로 분기해야 하고, 모드를 추가하거나 바꿀 때 놓치는 곳이 생긴다.
2. **모드를 인자로 받는 공용 모듈(`libs/crypto`)**: 모드가 "어떤 알고리즘 조합이 필요한가"만 결정하고, 서명·키 교환·암호화 코드는 하나다. 게이트웨이와 시뮬레이터가 같은 코드를 쓴다.

HYBRID 키 결합 방식:

1. **두 공유 비밀을 XOR**: 단순하지만 한쪽 비밀이 예측 가능하면 결합 결과의 성질을 설명하기 어렵다.
2. **두 공유 비밀을 이어 붙여 HKDF로 키 유도**: 한쪽이 깨져도 다른 쪽 비밀이 남아 있으면 결과 키를 알 수 없다. TLS 하이브리드 키 교환 초안들이 쓰는 방식과 같다.

## 결정

선택지 2(공용 모듈)와 HKDF 결합을 쓴다.

**알고리즘**

| 용도 | LEGACY | HYBRID | PQC |
| --- | --- | --- | --- |
| 서명 | RSA-2048 (`SHA256withRSA`) | RSA-2048 **와** ML-DSA-65, 둘 다 통과해야 성공 | ML-DSA-65 |
| 키 교환 | RSA-2048 OAEP(SHA-256)로 32바이트 비밀 전달 | RSA OAEP **와** ML-KEM-768 | ML-KEM-768 |
| 세션 키 유도 | HKDF-SHA256 | HKDF-SHA256(두 비밀을 이어 붙임) | HKDF-SHA256 |
| 본문 암호화 | AES-256-GCM | AES-256-GCM | AES-256-GCM |

- RSA-2048은 지금 은행 시스템에서 많이 쓰는 강도라 "전환 전" 기준으로 둔다. ML-KEM-768, ML-DSA-65는 NIST 보안 3등급이고 W1 PoC(`poc-bc-check`)에서 동작을 확인했다.
- 서명의 `alg` 값은 전문 규격대로 `RSA`, `ML-DSA`를 쓴다.

**규칙**

1. **모드가 요구하는 알고리즘 집합과 정확히 같아야 한다.** 빠져도, 더 있어도, 같은 알고리즘이 두 번 있어도 거부한다. HYBRID 요청에 RSA 서명만 붙이는 다운그레이드를 막는다(T2).
2. **세션 키 유도에 모드 이름과 모든 캡슐(ciphertext)을 넣는다.** HKDF의 `info`에 `pqc-transfer/v1`, 모드 이름, 캡슐 바이트를 넣어서, 같은 비밀이라도 모드가 다르면 다른 키가 나오고 캡슐을 바꿔 끼우면 키가 달라진다(T2).
3. **HYBRID 세션 키는 RSA 비밀만으로 복원되지 않는다.** 양자컴퓨터로 RSA를 깨도 ML-KEM 비밀을 모르면 키를 알 수 없다(T1).
4. **AES-GCM의 IV는 암호화할 때마다 12바이트 난수로 만든다.** 출력은 `IV || 암호문(태그 포함)`이다. 추가 인증 데이터(AAD)는 호출하는 쪽이 넘긴다.
5. **키는 `KeyProvider` 인터페이스로만 얻는다.** 키는 `kid`(키 번호)로 찾는다. 구현은 환경변수에서 읽는 것과 시험용 메모리 저장 두 가지다(위협 모델 7장 2번 결정). 실제 키 서비스나 HSM은 범위 밖이다.
6. **HYBRID의 RSA 사용은 의도된 것이다.** 진단 규칙에 걸리지 않도록 해당 줄에 `nosemgrep` 주석을 단다(`tools/diagnosis/results/rule-test-results.md`의 규격 반영 부분).

## 결과와 트레이드오프

- 얻는 것: 게이트웨이는 모드 값만 넘기면 되고, 모드별 차이는 한 곳(`CryptoMode`)에만 있다. 위협 T1, T2, T5의 검증 방법을 단위 테스트로 만들 수 있다.
- 감수하는 것: HYBRID는 서명 2개, 캡슐 2개를 만들고 검증하므로 LEGACY보다 느리고 전문이 크다. 크기와 속도는 W9 성능 측정(M5)에서 잰다.
- 아직 정하지 않은 것
  - 키 교환을 어떤 HTTP 요청으로 주고받을지(세션 만들기 API)와 `session_id` 발급 방식. 전문 규격에 추가해야 하므로 W3 게이트웨이 작업 때 팀원과 정한다.
  - 서명 대상의 JCS(RFC 8785) 정규화는 게이트웨이에서 한다. 이 모듈은 정규화가 끝난 바이트를 받는다.
  - 세션 키 캐시(유효기간, 사용 횟수)는 W5에 정한다.
- 다시 볼 조건: Bouncy Castle이 ML-KEM·ML-DSA API를 바꾸거나, 표준 하이브리드 결합 방식(예: IETF 초안)이 확정되면 결합 방식을 맞춘다.
