# 위협 모델 (v0.1, W1 초안)

> 목적: 코드를 짜기 전에 **무엇을 지키고, 누가 어디를 공격하며, 무엇으로 막고, 어떻게 증명할지**를 정한다.
> 범위: 이 문서는 학습·포트폴리오용 시스템(기업 펌뱅킹 보안 게이트웨이)에 대한 것이다. 실제 은행 운영 환경을 대상으로 하지 않는다.
> 상태: 초안. 팀원 검토 후 확정하고, 설계가 바뀌면 이 문서도 같이 고친다.

## 1. 지킬 것 (자산)

| ID | 자산 | 왜 중요한가 |
| --- | --- | --- |
| A1 | 이체 요청·응답 데이터 (계좌, 금액) | 도청되면 거래 정보 유출, 변조되면 금전 피해 |
| A2 | 원장(잔액·분개) | 금액이 틀어지면 서비스 신뢰가 깨짐 |
| A3 | 암호키·서명키 | 유출되면 모든 보호가 무력화됨 |
| A4 | 감사 로그 | 사고 때 "누가 무엇을 했는지"의 유일한 증거 |
| A5 | 암호 진단 결과(어느 코드가 취약한지) | 공격자에게 약점 지도가 됨 |

## 2. 구조와 신뢰 경계

```
[외부망: 기업 고객 시스템]
        │  (TLS + 하이브리드 키 교환)         ← 경계 ①: 신뢰할 수 없는 영역
[DMZ: 보안 게이트웨이]   복호화·서명 검증만 수행, 데이터 저장 안 함
        │  (내부 인증 통신)                    ← 경계 ②
[내부망: 이체 API · 원장 DB · 결재]
        │
[관리망: 어드민 · 진단 도구 · 모니터링]        ← 경계 ③: 관리자만 접근
```

원칙: **게이트웨이는 복호화만 하고, 원장은 내부망 밖으로 나오지 않는다.**

## 3. 공격자 가정

| 유형 | 할 수 있는 것 | 할 수 없다고 가정하는 것 |
| --- | --- | --- |
| 외부 도청자 | 외부망 트래픽 수집·저장, 재전송, 변조 시도 | 내부망 접근 |
| 능동 공격자 | 요청을 가로채 바꾸거나 모드 협상을 방해 | 서버의 개인키 탈취 |
| 내부 사용자 | 정상 권한으로 이체 생성·승인 | 감사 로그 DB를 직접 수정 |
| 미래의 양자 공격자 | 저장된 RSA·ECC 트래픽의 해독 | AES-256, ML-KEM의 해독 |

## 4. 위협과 대응 (핵심 13개)

우선순위 **H**=반드시 구현·검증, **M**=구현 권장, **L**=문서화만.

| ID | 위협 | 공격 방식 | 대응 (설계) | 검증 방법 | 우선 |
| --- | --- | --- | --- | --- | --- |
| T1 | **HNDL** (수집 후 해독) | 현재 트래픽을 저장했다가 양자컴퓨터로 해독 | HYBRID 모드(RSA + ML-KEM) 키 교환, 데이터는 AES-256-GCM | HYBRID 세션의 키가 ML-KEM 없이 복원되지 않음을 단위 테스트로 확인 | H |
| T2 | **다운그레이드** | 협상을 가로채 약한 모드로 강제 | 모드 협상 값을 서명 범위에 포함, 정책상 최저 모드 설정, 불일치 시 거부 | 변조된 협상 요청이 거부되는지 테스트 | H |
| T3 | **재전송(replay)** | 가로챈 이체 요청을 다시 전송 | `timestamp`가 서버 시각 ±5분 밖이거나, 서명 검증 뒤 Redis에 10분 보관하는 `nonce`가 재사용되면 거부(둘 다 `E1002`). 이체는 멱등성 키 + DB 유니크 제약 | 동일 요청 2회 전송 시 `E1002` 또는 이체 1건만 생성 | H |
| T4 | **중복·동시 요청** | 네트워크 재시도로 같은 이체가 두 번 처리 | 멱등성 키 + 트랜잭션 격리 | 동시 1,000건 이상(재시도·중복 요청 포함)에서 중복 0건 | H |
| T5 | **요청 변조** | 금액·계좌를 중간에서 변경 | ML-DSA와 RSA 서명 모두 검증(HYBRID), 본문 해시 서명 | 본문 1비트 변조 시 검증 실패 | H |
| T6 | **내부자 단독 이체** | 한 명이 생성과 승인을 모두 수행 | 결재(maker-checker): 생성자와 승인자 분리, 한도별 승인 | 같은 사용자 승인 시 거부 | H |
| T7 | **감사 로그 위·변조** | 흔적 삭제 | 해시 체인 로그(이전 로그 해시를 다음에 포함), 추가 전용 | 중간 행을 수정하면 체인 검증 실패 | H |
| T8 | **원장 불일치** | 장애·버그로 잔액이 틀어짐 | 복식부기(차변=대변), 일일 대사(reconciliation) 배치 | 의도적 오류 주입 시 대사 배치가 탐지 | H |
| T9 | **키 유출** | 소스·로그·저장소에 키 노출 | 키는 코드 밖(환경변수/시크릿)에서 키 관리 인터페이스로 주입하고 `kid`로 구분, `.gitignore`, 로그 마스킹, 키 회전 절차 | 저장소·로그 스캔에 시크릿 0건 | H |
| T10 | **전환 중 장애** | 암호 모드 전환 시 진행 중 요청 실패 | 기업별 모드 스위치, 전환 기간에는 구·신 모드 병행 허용, 롤백은 모드 값을 되돌림 | 전환 중 부하 테스트에서 실패율 목표 이하 | M |
| T11 | **진단 누락** | 진단 도구가 취약 코드를 못 찾음(탐지 실패) | 규칙 스캐너를 기본으로 하고 AI는 보조, 정답 라벨 데이터로 재현율 측정 | 라벨 세트에서 재현율·오탐률 측정 | M |
| T12 | **서비스 거부(DoS)** | 대량 요청으로 PQC 연산(키 생성·서명) 부하 유발 | 게이트웨이 앞단 속도 제한, 타임아웃, 세션 재사용 | k6 부하 시험에서 한도 초과 요청이 거절됨 | L |
| T13 | **내부자 단독 정책 변경** | 관리자 한 명이 기업의 허용 최저 모드(`crypto_floor`)나 승인 정책을 낮춤 | 보안 정책 변경에도 maker-checker 적용(요청자와 승인자 분리, `policy_change_request` 테이블), 변경 내역을 감사 로그에 기록 | 같은 사용자가 요청·승인 시 거부, 변경 기록이 감사 로그에 남음 | H |

## 5. 범위 밖 (이번 프로젝트에서 하지 않는 것)

- 실제 금융망 연동, 금융보안원 인증, HSM 실장비(대신 키 관리 인터페이스만 두고 소프트웨어로 대체)
- 양자컴퓨터 자체에 대한 방어 시험(알고리즘 표준을 신뢰하고, 구현 정합성만 검증)
- 물리 보안, 사회공학, 직원 계정 탈취 대응 전반
- 사이드채널 공격 대응(Bouncy Castle 구현을 신뢰)

범위 밖은 "안 한다"고 **명시**해 두는 것이 중요하다. 면접에서 한계를 아는 것으로 보인다.

## 6. 이 문서에서 나오는 검증 지표 후보

- HYBRID 키 교환 성공률, 다운그레이드 시도 거부율 (T1, T2)
- 중복 이체 0건 (T3, T4)
- 변조 요청 거부율 100% (T5)
- 미승인 정책 변경 차단율 100% (T13)
- 대사 불일치 탐지율 (T8)
- 저장소·로그 시크릿 0건 (T9)
- 모드 전환 중 실패율, HYBRID vs RSA 지연·TPS 비교 (T10, 성능)
- 진단 재현율·오탐률 (T11)

## 7. 팀 결정 사항

1. **우선순위 H 10개는 모두 유지한다.** 대부분 단위·통합 테스트로 검증할 수 있고, 무거운 것은 T4(동시 1,000건 부하 시험)와 T8(대사 배치) 정도다. W7 통합 관문까지 검증하지 못한 H는 M으로 내린다.
2. **키 관리는 키 관리 인터페이스(`KeyProvider`)와 환경변수 구현으로 한다.** 5절의 "HSM 대신 키 관리 인터페이스만 두고 소프트웨어로 대체"와 같은 방침이다. 전문 규격의 `kid`(키 번호)로 키를 찾게 해서 T9의 키 회전까지 대응한다.
3. **T10은 모드 스위치와 병행 허용 기간까지만 구현한다.** 서버를 한 대씩 교체하는 롤링 배포는 2인 12주 규모에 비해 과하다. 기업별로 전환 기간 동안 구·신 모드를 둘 다 허용하고, 기간이 끝나면 신 모드만 허용한다. W10 "부하 중 모드 전환" 시험으로 검증한다.
4. **T13은 정책 변경 전용 테이블을 추가하고 우선순위 H를 유지한다.** `policy_change_request`에 대상 기업, 바꿀 항목, 이전 값과 새 값, 요청자, 승인자, 상태를 기록한다. 기존 `approval`을 이체·정책 공용으로 넓히면 `transfer_id`가 비어 있을 수 있고 R4(요청자 ≠ 승인자) 제약도 복잡해져서 따로 둔다. 이체 결재와 같은 규칙이라 추가 부담이 작고, 빠지면 관리자 혼자 `crypto_floor`를 낮춰 T2 방어를 무력화할 수 있다. ERD 반영은 ERD 담당 팀원이 한다.

## 8. 용어 (처음 보는 사람용)

- **HNDL**: Harvest Now, Decrypt Later. 지금 암호문을 모아 두었다가 나중에 해독.
- **ML-KEM / ML-DSA**: 양자컴퓨터에 안전한 키 교환 / 전자서명 표준(FIPS 203, 204).
- **HYBRID**: 기존(RSA)과 신규(ML-KEM)를 함께 써서, 둘 중 하나가 깨져도 안전하게 하는 방식.
- **멱등성(idempotency)**: 같은 요청을 여러 번 보내도 결과가 한 번 처리한 것과 같은 성질.
- **maker-checker**: 만드는 사람과 승인하는 사람을 분리하는 통제.
- **복식부기 / 대사**: 모든 거래를 차변·대변 두 줄로 기록해 합이 맞는지 검증 / 매일 장부를 맞춰 보는 작업.
