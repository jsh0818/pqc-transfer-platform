# 이체 전문 규격 (v0.2, W1 초안. 팀원 피드백 반영)

> 목적: 기업이 은행(우리 게이트웨이)에 보내는 이체 요청과 그 응답의 항목·형식·오류 코드를 정한다.
> 이 문서가 확정되면 OpenAPI(`docs/api/openapi.yaml`)와 DB(`docs/erd/erd.md`)가 이것에 맞춰진다.
> 상태: 초안. 형식은 JSON으로 가정한다. API 계약은 `docs/api/openapi.yaml`에 같은 내용이 있다. 팀 검토 후 W1 말 "계약 확정"에서 고정한다.

## 1. 흐름

```
기업 시스템 ──(1) 이체 요청(서명 포함)──▶ 게이트웨이(DMZ)
                                        │ 서명 검증, 재전송 검사, 모드 검사, 복호화
                                        ▼
                                    이체 API(내부망) ── 결재 필요? ── 원장 기록
기업 시스템 ◀──(2) 응답(접수 결과)─────────┘
기업 시스템 ──(3) 상태 조회(서명 포함)──▶ 처리 결과 확인 (승인 대기 중일 수 있음)
```

- 승인이 필요한 이체는 요청 직후 `PENDING_APPROVAL`로 응답하고, 이후 상태 조회로 최종 결과를 확인한다.
- 같은 `idempotency_key`로 다시 보내면 새로 처리하지 않고 기존 결과를 돌려준다.

## 2. 요청 (Request)

### 2-1. 보안 정보 (`security` 객체, 게이트웨이가 검사)

> 논리적으로는 이체 내용과 분리된 보안 메타데이터다. HTTP에서는 헤더가 아니라 요청 본문의 `security` 객체로 보낸다. HYBRID 서명(RSA + ML-DSA)이 base64로 약 4.8KB라서 헤더 한도(보통 8KB)에 가깝기 때문이다. 서명 대상은 `security`(서명 제외)와 `transfer`를 **RFC 8785(JCS)** 로 정규화한 바이트이고(직접 구현하면 양쪽 결과가 달라질 수 있어 표준을 쓴다), `crypto_mode`도 포함되어 다운그레이드를 막는다.

| 항목 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `crypto_mode` | 문자열 | O | `LEGACY`, `HYBRID`, `PQC` 중 하나. 기업의 허용 최저 모드(`crypto_floor`) 미만이면 거부 |
| `session_id` | 문자열 | O | 키 교환으로 만든 세션 식별자 |
| `timestamp` | 문자열(ISO 8601, UTC) | O | 요청 시각. 서버 시각과 차이가 5분(앞뒤)을 넘으면 거부 |
| `nonce` | 문자열 | O | 요청마다 새로 만드는 일회용 값. 서명 검증 뒤 Redis에 10분간 보관하고, 이미 쓴 값이면 거부(재전송 차단) |
| `signatures` | 배열 | O | `{alg, kid, value}` 목록. `alg`는 알고리즘, `kid`는 서명에 쓴 키 번호(키·알고리즘 교체 대비). `LEGACY`는 RSA 1개, `HYBRID`는 RSA와 ML-DSA **둘 다 통과해야 성공**(하나만 통과해도 되면 하이브리드 의미가 없음), `PQC`는 ML-DSA |

### 2-1-1. 상태 조회 요청

상태 조회도 같은 `security` 객체로 서명하고, 본문의 `inquiry` 객체(`transfer_id`, `corporation_id`)를 이체의 `transfer` 자리에 둔다. 서명 대상은 `security`(서명 제외)와 `inquiry`를 JCS로 정규화한 바이트다. 검증 순서(5장)도 같다.

- `POST /v1/transfers/{transferId}/status`를 쓴다. 조회인데 GET이 아닌 이유는 HYBRID 서명이 헤더 한도에 가깝기 때문이다(위 안내).
- `inquiry.transfer_id`는 경로의 `transferId`와 같아야 한다. 서명 범위에 들어가므로 경로만 바꿔 다른 이체를 묻는 것을 막는다. 다르면 `E1000`.
- 서명한 기업(`corporation_id`)의 이체만 조회된다. 다른 기업의 이체와 없는 이체는 구분 없이 `E2008`(404)로 답해 존재 여부를 알려주지 않는다.
- 어드민은 이 API를 쓰지 않는다. 어드민은 결재 API(8081)와 관리망 경로로 본다.

### 2-2. 이체 내용 (`transfer` 객체)

| 항목 | 타입 | 필수 | 제약 | DB 매핑 |
| --- | --- | --- | --- | --- |
| `idempotency_key` | 문자열 | O | 기업 안에서 유일, 8~64자 | `transfer_request.idempotency_key` |
| `corporation_id` | 숫자 | O | 인증된 기업과 같아야 함 | `corporation.id` |
| `from_account_no` | 문자열 | O | 해당 기업 소유 계좌, ACTIVE | `account.account_no` |
| `to_bank_code` | 문자열 | O | 3자리 은행 코드 | `to_bank_code` |
| `to_account_no` | 문자열 | O | 숫자만, 10~16자 | `to_account_no` |
| `amount` | 문자열 | O | 원 단위 정수를 문자열로("1500000"), 앞자리 0·소수점 없음, 최대 15자리. DB에는 정수로 저장 | `amount` |
| `currency` | 문자열 | O | 초안은 `KRW`만 허용 | `account.currency` |
| `memo` | 문자열 | X | 최대 20자 | (선택) |
| `requested_at` | 문자열(ISO 8601) | O | 기업 시스템이 요청을 만든 시각 | `requested_at` |

### 2-3. 예시 (`transfer` 객체 부분. 전체 구조는 `openapi.yaml` 참고)

```json
{
  "idempotency_key": "ACME-20261123-000123",
  "corporation_id": 1001,
  "from_account_no": "1002345678901",
  "to_bank_code": "088",
  "to_account_no": "1109876543210",
  "amount": "1500000",
  "currency": "KRW",
  "memo": "11월 거래대금",
  "requested_at": "2026-11-23T05:50:12Z"
}
```

## 3. 응답 (Response)

| 항목 | 타입 | 설명 |
| --- | --- | --- |
| `result_code` | 문자열 | 4장의 코드 |
| `message` | 문자열 | 사람이 읽는 설명 |
| `transfer_id` | 숫자 | 접수된 이체 ID. 실패로 접수가 안 된 경우 없음 |
| `status` | 문자열 | `REQUESTED`, `PENDING_APPROVAL`, `APPROVED`, `POSTED`, `REJECTED`, `FAILED` (ERD의 상태 흐름과 같음) |
| `processed_at` | 문자열(ISO 8601) | 서버 처리 시각 |

```json
{
  "result_code": "0000",
  "message": "이체 요청이 접수되었습니다",
  "transfer_id": 52001,
  "status": "PENDING_APPROVAL",
  "processed_at": "2026-11-23T05:50:13Z"
}
```

## 4. 결과 코드 (초안)

| 코드 | 의미 | 어디서 막나 | 위협 모델 |
| --- | --- | --- | --- |
| `0000` | 정상 접수 | | |
| `E1001` | 서명 검증 실패(변조 의심) | 게이트웨이 | T5 |
| `E1002` | 재전송 의심(`nonce` 중복 또는 `timestamp` 범위 초과) | 게이트웨이 | T3 |
| `E1003` | 허용되지 않은 암호 모드(최저 모드 미만, 협상 불일치) | 게이트웨이 | T2 |
| `E2001` | 중복 요청. 기존 결과를 함께 반환 | 이체 API | T3, T4 |
| `E2002` | 잔액 부족 | 이체 API | |
| `E2003` | 승인 필요(`PENDING_APPROVAL`로 접수됨) | 결재 엔진 | T6 |
| `E2004` | 한도 초과 | 결재 엔진 | |
| `E2005` | 계좌 상태 이상(동결 등) 또는 소유 불일치 | 이체 API | |
| `E1000` | 형식 오류(필수 항목 누락, 제약 위반) | 게이트웨이 | |
| `E2006` | 작성자와 승인자가 같음 | 결재 엔진 | T6 |
| `E2007` | 이미 처리된 이체라 결재 불가(상태 불일치) | 결재 엔진 | |
| `E2008` | 이체를 찾을 수 없음 | 이체 API | |
| `E9000` | 서버 내부 오류. 같은 `idempotency_key`로 재시도 가능 | 전체 | |

`E2001`은 오류가 아니라 **안전한 재시도의 결과**이므로, 기업 시스템은 같은 키로 다시 보내도 이체가 한 번만 일어난다고 믿을 수 있어야 한다.

**외부 응답 정책**: 코드는 위처럼 세분화하지만, 보안 검사 실패(`E1001`~`E1003`)의 외부 `message`는 "요청을 확인할 수 없습니다"처럼 원인을 알려 주지 않는다. 어느 서명이 틀렸는지, 최저 모드가 무엇인지는 공격자에게 힌트가 되므로 내부 감사 로그에만 자세히 남긴다.

## 5. 검증 순서 (게이트웨이와 이체 API)

1. `crypto_mode`가 허용 범위인가 → 아니면 `E1003`
2. `timestamp`가 5분 범위 안인가 → 아니면 `E1002`
3. 모든 필수 서명이 유효한가(HYBRID는 둘 다) → 아니면 `E1001`
4. `nonce`를 처음 보는가 → 처음이면 Redis에 10분 보관, 이미 있으면 `E1002`. **서명 확인 뒤에 등록**한다. 서명 전에 저장하면 가짜 요청이 nonce를 선점해 정상 요청이 막힌다
5. 복호화 후 본문 항목이 제약을 지키는가 → 아니면 `E1000`
6. `idempotency_key`가 이미 있는가 → 있으면 `E2001`과 기존 결과
7. 계좌·잔액·한도·승인 정책 검사 → `E2002`, `E2004`, `E2005`, `E2003`
8. 원장 기록과 `POSTED`

## 6. 팀이 정할 것

1. (확정) `timestamp` 5분, `nonce` Redis 10분 보관. 남은 일: Docker Compose에 Redis 추가
2. `idempotency_key` 형식 규칙을 강제할지
3. 기존 방식의 고정 길이 전문 형식을 따로 지원할지, JSON만 쓸지(W3 "LEGACY 미니 통합" 전에 결정)
4. 타 은행 이체의 은행 코드 목록 범위
5. 결과 코드 번호 체계(초안은 임의로 붙인 값)
